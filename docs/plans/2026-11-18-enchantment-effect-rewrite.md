# 附魔效果改寫執行計畫（Luna）

## 目標與狀態

進行中，待執行。以 Echo 為句型範例，逐筆審查 124 個附魔，把有來源的玩家與怪物效果寫成可直接理解的雙語短句。每個附魔都要有查核結果。依[附魔效用規格](../specs/enchantment-availability.md)決定顯示哪一側。

## 改動邊界

- 以 `content/catalog.sqlite` 為正式資料來源。`enchantment_effect_profiles` 指向顯示用的 fact ID，文案寫入該 fact 的 `fact_translations.value`（`en`、`zh-Hant`）。同條目可能有兩筆同語意的 facts，逐一按 fact ID 查核，保留每筆既有證據及用途。
- 以[來源稽核](../audits/enchantment-effect-facts.json)的固定版次、節名、摘錄與階級表為起點。稽核的 `claim` 同步至最終文案，摘錄保留來源原貌。必要時同步既有稽核產生器與測試 fixture 的對應期待值，保持可重跑。
- 沿用 SQLite schema、詳情呈現政策、UI 與匯出流程。武器、盔甲、圖標、Wiki 原文、排序、關聯及條目 ID 在本輪範圍之外。

## 步驟與驗證

### 1. 定稿句型並試寫

每側先寫一個完整句子，依序交代「觸發條件 → 效果 → 目標或限制」。將已確認的機率、倍率、冷卻、持續時間、範圍或階級差異接在效果後。機制較多時可拆成第二句。英文與繁體中文使用同一組條件、數字和單位。階級依 I、II、III 排列，明示各數字代表的量。保留來源的「可能」「最多」「僅限」等限定語。效果列標題由既有畫面提供。

| 樣本 | 應驗證的輸出 |
| --- | --- |
| Echo（回聲） | 玩家攻擊後可能自動補一次攻擊，I／II／III 階冷卻分別為 5／4／3 秒。怪物攻擊後立即補一次攻擊。怪物冷卻與觸發限制未確認，關係維持 `unknown`。 |
| Critical Hit | 玩家三階機率分別為 10%／15%／20%，觸發時造成三倍傷害。怪物每次攻擊都造成三倍傷害。兩側各有佐證，關係為 `different`。 |
| Ambush | 保留兩側各自的來源及怪物效果的 `[verify]`，可用性衝突放在「更多資訊」。 |
| 從現有 profile 各選一筆同效、僅玩家、僅怪物、無直接佐證 | 核對顯示分支。未使用條目仍列入查核清單。 |

Echo 的英文基準為使用者提供的兩句。玩家的階級冷卻出自固定版附魔總表，怪物行為出自固定版附魔怪物頁。後者的原文僅支持補打行為與時機。 [附魔總表固定版](https://minecraft.wiki/w/Dungeons:Enchantment?oldid=3899779) [附魔怪物固定版](https://minecraft.wiki/w/Dungeons:Enchanted?oldid=3747433)

### 2. 逐批查核

1. 從 SQLite 匯出 124 個 profile 與所有雙側效果 facts 作為清單。按 `entry_id` 排序，每批最多 12 筆附魔，以上一批最後一個 ID 續跑。開始前記錄總數與各 fact 的原值，避免把同語意的不同 fact 當成重複資料。
2. 每側先比對稽核摘錄和永久連結，再寫雙語效果。逐項核對觸發、目標、數值、單位、階級和例外。遇到缺文、衝突或存取失敗，保存已核實部分及原因。只有怪物可用清單時，只記可用性證據。
3. 每筆記錄條目 ID、兩側 fact ID 或 `NULL`、雙語新舊值、來源版本與節名、待查標記及決定（已改寫／已核對沿用／不可用／未確認）。來源、可用性或關係若有新發現，附具體證據並列為待審，避免混入純文案批次。每批完成後用清單核對條目覆蓋，未確認項給出具體理由。

| 證據狀況 | Luna 必須採用的處理 |
| --- | --- |
| 兩側有來源且同效 | 保留各側查核資料，由既有版面顯示玩家效果及怪物同效附註。 |
| 兩側有來源且不同，或關係未知 | 主欄同層顯示兩側。未知的關係在「更多資訊」明示。僅一側記載某個數值時，另一側保持未確認。 |
| 一側明確不可用 | 依既有政策顯示另一側。Wiki 清單缺項不足以判定不可用。 |
| 存在 `[verify]`、來源衝突或僅有推論 | 保留來源標記和衝突紀錄。有 `supports` 的效果依既有政策呈現；推論與未知依既有政策收在「更多資訊」。 |

### 3. 寫入與驗收

1. 先在資料庫副本試寫。以交易和參數化 SQL 按 fact ID、語言與預期舊值更新，核對受影響列數，任一列不符就整批回滾。雙語一起變更。保留未改寫的 facts 與證據；正式寫入依 repo 的資料變更授權執行。
2. 比對改寫前後資料。124 個 profile 皆有查核結果，原有 fact ID 與每側關聯皆能追溯。核對改寫、沿用、不可用及未確認的數量，列出未確認清單；檢查其餘資料表及欄位差異為零。對新證據的變更另行驗收。
3. 跑 `npm test`、`npm run build`。直接讀取本地 `dist/index.html`、附魔條目 JSON 與 `dist/src/file-app.js`，不開瀏覽器。比對 HTTP 靜態條目與本機資料包輸出相同。逐筆核對效果順序及分支，並抽驗 Echo、Critical Hit、Ambush 和步驟一的各類樣本。主欄、相關條目、預設收合的「更多資訊」、來源維持既有順序。

## 切換與回退

沿用既有建置與載入路徑。每批查核紀錄保留雙語舊值。若交易失敗則回滾該批，已發布時還原對應資料提交並重新建置。
